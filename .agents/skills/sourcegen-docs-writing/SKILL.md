# SourceGen Docs Writing

Audience: developers **new to the library**. Optimize for clarity, progressive disclosure, and practical examples.

## Layout

| Item | Convention |
|---|---|
| Site | VitePress; sources under `docs/`, config in `docs/.vitepress/config.ts` |
| Domain folder | `docs/<Domain>/` (e.g. `docs/Ioc/`) |
| File names | `NN_Name.md` with a two-digit order prefix (e.g. `01_Overview.md`, `05_Keyed.md`); one feature per file |
| Entry point | `01_Overview.md` — its `## Table of Contents` table (`Document` / `Description`) MUST list every doc in the folder |
| Sidebar | Add every new page to the sidebar in `docs/.vitepress/config.ts` (link without `.md`, e.g. `/Ioc/05_Keyed`) |
| Footer | Every non-overview doc ends with `---` followed by `[← Back to Overview](01_Overview.md#table-of-contents)` |

When adding a page, update **all three**: the new file, the Overview Table of Contents, and the VitePress sidebar. Ask before renumbering existing files or adding a file that does not fit the current numbering.

## Progressive Disclosure

- Open each document with the simplest working example.
- Introduce advanced options gradually; keep paragraphs short and headings scannable.
- Link to prerequisite docs instead of re-explaining earlier concepts.

## Generated Code Sections

For every source-generator feature, show the generated output in a collapsible block placed right after the user-facing example:

````markdown
<details>
<summary>Generated Code</summary>

```csharp
// <auto-generated/>
// ... generated registration code ...
```

</details>
````

## Markdown Style

- GitHub-flavored Markdown.
- Callouts: `> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`.
- Fenced code blocks with the `csharp` language tag.
- Tables for reference data (attributes, diagnostics, options).
- `<details>` / `<summary>` for generated code and advanced details.

## Accuracy

- Verify every attribute, option, diagnostic, and example against the specs (`**/Spec/*.spec.md`) and source before writing.
- Prefer examples that mirror `samples/` or test cases so they are known to compile.
- Never document features that do not exist; flag uncertain behavior instead of guessing.
